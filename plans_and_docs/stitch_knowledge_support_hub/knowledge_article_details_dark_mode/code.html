Database Connection Timeout Troubleshooting

schedule Last updated: 2 hours ago by Sarah Jenkins
visibility 1.2k views
High Priority PostgreSQL

info Issue Summary

Applications fail to connect to the primary PostgreSQL cluster during peak load hours (typically 09:00 - 11:00 UTC). The issue manifests as `ETIMEDOUT` errors in the application logs and increased latency in downstream services dependent on database queries.

warning Symptoms

  • Application logs show repeated connection refused or timeout errors.
  • Datadog dashboards show connection pool utilization hitting 100% capacity.
  • End-users experience 504 Gateway Timeout errors on read-heavy endpoints.

dns Environment

Database Engine:
PostgreSQL 14.8
Hosting:
AWS RDS (Multi-AZ)
Instance Type:
db.r6g.4xlarge
Connection Pooler:
PgBouncer 1.18

search Root Cause

The `max_connections` parameter on the RDS instance is misaligned with the PgBouncer configuration. During traffic spikes, PgBouncer attempts to open more connections to the backend database than RDS allows, leading to immediate connection rejection and cascading timeouts in the application layer.

build Troubleshooting Steps

1

Verify current connection limits

Run the following query on the primary database to check the configured maximum limits versus active connections.

SELECT max_conn,used,res_for_super,max_conn-used-res_for_super res_for_normal 
FROM 
  (select count(*) used from pg_stat_activity) t1,
  (select setting::int res_for_super from pg_settings where name=$$superuser_reserved_connections$$) t2,
  (select setting::int max_conn from pg_settings where name=$$max_connections$$) t3;
2

Check PgBouncer logs

Access the bastion host and tail the PgBouncer logs looking for `server login failed: FATAL: sorry, too many clients already`.

check_circle Resolution

To resolve the issue permanently:

  1. Update the RDS Parameter Group to increase `max_connections` (e.g., to 2000).
  2. Adjust PgBouncer `max_client_conn` and `default_pool_size` in `pgbouncer.ini` to align with the new database limits, ensuring a 10% buffer.
  3. Restart PgBouncer service to apply configurations gracefully.
